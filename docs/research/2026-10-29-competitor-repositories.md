# Related NASA Space Apps repositories: source review and opportunities

Reviewed 2026-10-29 (Asia/Dhaka). Research only; no application or plan changes. Public materials can change. This is a bounded competitor sample, not a global novelty search or a forecast of judging results. The two user-supplied sites are being reviewed separately by the parent task; do not confuse the supplied CropSafe demo with unrelated commercial businesses sharing that name.

## Method and baseline

Inspected GitHub README files, repository trees and available implementation files. Explicitly separate running source-level interactions, project claims and illustrative scientific outputs. No competitor was installed or scientifically field-validated in this review. NASA-hosted team pages are self-described projects, not NASA endorsement of their performance.

Baseline for comparison: [our full 2026-10-29 plan](../plans/2026-10-29-nasa-planting-window-and-rotation.md). It already includes NASA multi-source context, historical distributions, GDD/onset, rotation scenarios, uncertainty, climate sliders, priority weighting, provenance, Bangla voice, offline safety, native delivery and existing operational tasks/problems. Those are not genuinely new additions just because another project has them.

## Opportunities: new versus already planned

The following are **proposals/inferences**, rather than features proven globally novel. The most defensible distinction is a better evidence-to-decision-to-action loop operating on real farmer state.

| Feature | Added behavior beyond our current plan | Source of inspiration / uniqueness limit | Owners and effort shape |
|---|---|---|---|
| **Rotation robustness envelope** | For each rotation, show the delay/heat/water constraint at which the calendar first becomes infeasible, the binding crop/stage, and a supported alternative. Compute a range over historical/scenario uncertainty rather than only one best-date recommendation | RotaShift already presents a sample Adaptation Margin, so this is new to us, not globally original. Differentiation would be a real, sourced, reproducible calculation and M3 action handoff | M2 pure compute, M4 scenarios, M5 explanation; medium once calendars/data exist |
| **Conditional Plan B with triggers** | A plan states observable conditions that would cause reevaluation: latest feasible transplant date, irrigation unavailable, or confirmed water constraint. A new supported observation opens a proposed switch with a precise reason and changed dates/tasks; farmer confirms | Our plan has alerts and confirmation, but not an explicit versioned contingency policy per selected rotation. Do not generate automatic crop switches or claim forecast certainty | M2 contingency policy → M3 state/version → M5 confirm; medium, high integration value |
| **Best next field question** | When unknown drainage/soil/irrigation changes the preferred option, ask the one safe farmer-observable question most likely to resolve the choice. Show “without this answer, these options remain tied” | More actionable than a passive evidence-gap badge. No need to claim trained Bayesian value-of-information if using transparent scenario/rule comparison | M1 progressive intake, M2 ambiguity analysis, M5 short question; low/medium using existing context |
| **Why not my crop? Minimal-change alternative** | Farmer names an intended crop/rotation; explain the binding constraints and smallest supported change that makes it feasible, such as a shorter-duration permitted variety or different date. If no evidence-backed change exists, say so | Goes beyond generic factor explanations and priority sliders. Do not recommend borrowing, buying water/equipment, or numeric costs without evidence | M2 feasibility search + M1 resources + M5 explanation; medium |
| **One shared pump, several farms** | Use the existing multi-farm account to compare overlapping irrigation/labor demands and propose a schedule within a declared capacity. Multiple households require explicit permissions before sharing farm details | No verified equivalent found in this limited source sample. This is a sample-relative observation, not proof of invention. It operationalizes water constraints rather than merely ranking crops | M1 pump capacity/availability → M2 resource feasibility → M3 confirmed tasks; larger but distinctive |
| **Historical case playback with forecast-safe matching** | Farmer selects a past year; app replays recorded daily weather and shows exactly where alternative calendars meet/fail constraints. If matching this year, only use information available up to today's seasonal cutoff | CropShift describes analog matching; Sky2Root shows a seeded replay interaction. Our parent plan already has historical validation, so playback is an extension, not an entirely absent science requirement | M2 replay adapter + M4 pinned data + frontend timeline; medium; avoid calling backtested suitability actual historical yield |
| **Portable decision record for farmer/extension worker** | A privacy-safe offline/printable decision card includes selected plan, action list, support state, result/cache versions and an optional authorized QR/reference. Another person can reproduce the same result without seeing unrelated farm data | BoponX and Space Hunters already have printable outputs. Our plan already has provenance/SMS; this only adds portable review/handoff and should be a smaller enhancement | Frontend share/export + M2 result ID; low/medium after typed results exist |
| **Season outcome and small-trial feedback** | Keep farmer-entered planting/harvest dates, observed failures and optional consented comparison-plot notes linked to the original recommendation; evaluate next-season timing errors against those records | Our project already stores season history and plans holdout validation. The incremental part is a versioned recommendation-to-observed-outcome feedback view. Observational records cannot establish causal benefit without an appropriate study | M1/M2 outcome/provenance + M3 check-ins; medium, longer-term evidence rather than immediate score decoration |

## Recommended selection

Complete required onset/GDD/rotation gates first. Then select at most three linked additions for the hackathon narrative:

1. Real rotation robustness envelope (decision depth).
2. One best next field question (reduces uncertainty without pretending to know soil).
3. A confirmed conditional Plan B flowing into the existing M3 tasks (execution and continued usefulness).

If available time only supports one addition, choose the **best next field question + minimal-change explanation** using already validated local rules; it can be small, testable and understandable. A full shared-resource scheduler or physical crop digital twin needs more evidence/implementation work and should not be bolted on as a fake demo.

Avoid treating 3D globes, more languages, another chatbot, badges/certificates, generic water-savings percentages or additional raw NASA layers as the principal novelty. Several competitors already display those; source inspection also shows why polished screenshots alone are weak evidence of scientific operation. Do not reproduce a “NASA verified” certificate or imply agency endorsement.

## Suggested demonstration and evidence

Show a real supported district/farm, two candidate rotations and an uncertainty about water access. The app asks one concrete question; the answer changes the feasible set. It shows which constraint would break the chosen rotation, a conditional alternative and the exact task changes. Farmer confirms; one M3 update is saved and visible in scoped chat. Source dates and uncertainty remain visible, and an unsupported case declines to invent an answer.

Measure correctness of the feasible-set transition, calendar/season isolation, duplicate confirmation behavior, understandable Bangla explanation, and end-to-end time on a real phone. This speaks directly to validity, relevance, UX and presentation without requiring an unverified crop-yield model. Winning remains a judging outcome, not something a feature list guarantees.

## Reuse discipline

Review ideas and source limitations; do not copy competitor visual assets, private farmer data or code without verifying its actual license and required attribution. Repository README claims of a license are not a substitute for an accessible license artifact. Retain attribution for any permitted reused material and describe independent implementation honestly.
